# Release 2: review draft, not deployment instructions

Do not deploy, migrate, change signup mode, pause the controller, or run production tests using this draft. The deployed original API is 271fb59, the worker is 64ecb15, and the replica controller currently reports wait-worker. All API containers reported RUN_MIGRATIONS=false. The proposed integration branch starts at 64ecb15 to preserve worker email suppression.

## Required before a sequence is approved

1. Finish and verify endpoint and existing-user regression tests, the full suite, disconnected-client behavior, and the approval scripts. Confirm that the proposed four-second wait and queue size are suitable; these are not measured production capacity.
2. Confirm current source commits, controller state, active ingress routing, and the migration ledger. The controller may refresh both replicas together and reactivate its route as soon as matching healthy API and worker versions satisfy its guards. It does not migrate or restore the original API.
3. Review migration 126 against a current production-compatible copy. Confirm backup freshness and recovery path. Existing APIs ignore the new signup policy, so neither a mixed-version deployment nor rollback enforces approved-only everywhere without independently verified ingress controls.
4. Review the signup-mode operator workflow and waitlist data. Oldest-N approval updates existing waitlist entries; explicit-email approval adds a separate signup access record, including for an address that is not on the waitlist. Neither creates a waitlist consent record or sends emails. Scripts print email addresses; protect their output. Basic concurrency and failure checks passed locally; audit and operational review remain.
5. Decide and approve a complete sequence with explicit per-step verification, failure recovery, controller handling, and the precise mode-switch point. Do not set approved_only until every possible account-creation path is confirmed to enforce it and rollback/ingress behavior is understood.
6. Define the scope and isolation of any live signup/login tests before execution. Approval of a proposed test does not establish safe test account creation, notification behavior, or cleanup.

## Verified local checks

Gate tests and Google identity regression passed against isolated PostgreSQL. Password signup endpoint cases passed locally for open, approved_only and closed; blocked cases created no account, waitlist entry or verification outbox row. Existing-user password login, password reset, and admin login passed in all three modes. Selected-email and oldest-N SQL scripts passed local checks including concurrent requests and invalid-limit rollback. Further tests remain required.

The real-socket disconnect test demonstrates that a request already waiting may execute after the client has disconnected. fasthttp's request Done channel is tied to server shutdown, not client disconnect. The queue and wait remain bounded; this is not cancellation. In particular an abandoned signup could create an account and queue verification. Review this behavior before release rather than claiming disconnected work is discarded.

Attempted mitigation: a 4096-byte body limit, reading the request body before waiting and checking both Fiber contexts after admission did not detect a real socket disconnect. The local signup endpoint then created one account and queued one verification email. This test did not include the production proxy. The inspected mobile source offers resend on a 409 signup conflict and a resend control on the sign-in screen; the installed phone build and end-to-end recovery still need verification. The user has accepted the disconnect behavior as non-blocking after this attempt; do not describe it as fixed.

## Candidate release order — not yet executable

1. Finalize and review the integrated source, commit it and obtain separate authorization before any push or deployment. Verify the worker changes from 64ecb15 remain present. Record the exact release commit and prior image IDs. No release commit exists at this point.
2. In a quiet window, take and verify a fresh backup. Recheck current routing, timer and controller ownership, migration history, and existing email/video/notification queues. Stop if the runtime differs from the reviewed assumptions. Confirm how to restore the original API image and the worker image 64ecb15; 271fb59 is not the current pre-release worker.
3. Apply reviewed migration 126 using a separately verified migration procedure, then confirm the ledger, default-open mode, retained existing rows and API readiness. The exact migration execution command and the live migration credentials/role have not been verified; do not improvise. A code rollback does not undo migration 126.
4. Deploy the reviewed worker commit while keeping the original API on its old commit. Verify its build identity, health, queue processing and suppression. The current controller should wait for matching API and worker commits; confirm this in the journal. If verification fails, restore the pre-release worker 64ecb15 and recheck queues. Confirm actual Coolify rollback controls before relying on them.
5. Deploy the original API at the same reviewed commit. Verify its build identity and readiness. Matching versions can trigger the controller automatically on its next timer event. Observe its journal, original API health, replica image IDs, replica health, and actual route; do not assume a one-by-one rollout or successful route reactivation. A failed refresh may leave traffic on the original API and can disable controller automation.
6. Verify all account-creation ingress paths enforce the new policy before setting approved_only; this is the earliest possible mode-switch point. The exact source of public traffic and a safe way to manage mixed-version rollback are still unverified. Until those are resolved, leave mode open and do not execute this candidate release plan.
7. The user has proposed five controlled signups and a 20-login test. Define isolated accounts, email destinations, rate, stop conditions, record handling and cleanup; obtain authorization for the concrete test before execution. Current production load tests have not been run.

Any failed readiness, unhealthy or repeatedly restarting service, unexpected controller/routing action, sustained email backlog, or inability to authenticate should stop the rollout and trigger assessment using the verified rollback procedure. A numerical rollback threshold and exact Coolify rollback clicks remain to be reviewed; do not assume switching both resources to an arbitrary old commit safely restores the prior state.
