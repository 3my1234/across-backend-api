## Cause and scope of the conclusion

`internal/routes/routes.go` creates a separate `NewAdmission(2)` password bulkhead for each API and applies it to login/signup/reset routes. `internal/middleware/admission.go` rejects excess concurrent operations immediately with JSON503 and `Retry-After:2`, before the password handler. The lab has two API replicas. This protects CPU-bound password work from taking over unrelated request slots.

The generator submits100logins together and aborts on the first login that does not return its expected200/identity/token. The raw k6 series records that login503; server logs also show numerous fast login503s during startup. Those logs include overlapping lifecycle checks, so they must not be treated as a clean count of measured login attempts or substitute for client completions.

This identifies a **login-arrival/admission constraint**, not PostgreSQL exhaustion. It does not establish the maximum sustainable login rate, how actual mobile clients retry, the steady-state capacity of100already authenticated users, or capacity at500users. Raising/removing the protective limit without a measured plan is not recommended.

The harness's immediate abort means latency/error threshold windows cannot develop. Content/authorization setup passed, but the normal-load zero503 gate failed and the user population was not established. Empty polling and per-operation metrics cannot count as successful qualification.
